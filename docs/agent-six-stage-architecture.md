# 气象智能体六阶段建设说明

本文档说明气象灾害个例问答智能体的阶段化建设思路、各阶段职责、核心产物和验收标准。这里沿用项目讨论中的 `0-6` 编号：`0` 是前置准备阶段，`1-6` 是六个正式建设阶段。

## 总体目标

智能体不是简单把检索片段拼给用户，而是要先理解用户问题，再选择合适的数据层和工具链路，最后组织成自然、准确、可追溯的业务回答。

目标效果：

- 能识别一句话中的一个或多个意图，例如统计、对比、证据检索、单过程复盘、相似个例和服务提示。
- 统计类问题走 `standard_cases` 全量过滤和聚合，不走 `top_k chunk`。
- 证据检索类问题能关联图片元数据，例如雷达图、卫星云图、降水图。
- 回答中区分结构化事实、检索证据、模型分析和证据缺口。
- 没有证据时明确说明缺失，不编造结论。
- 调试侧能看到识别了什么意图、用了哪些工具、跳过了哪些工具、每个子链路是否成功。

## 阶段 0：基础盘点和数据分层

阶段 0 是建设前的准备工作，重点是确认系统里有哪些可复用能力，以及每类问题应该优先依赖哪一层数据。

核心工作：

- 盘点已有服务：`standard_cases`、图片元数据、文档 chunk、相似个例匹配、会话存储、前端聊天面板。
- 明确数据分层：标准化个例用于统计和结构化判断；图片元数据用于图像证据；文档 chunk 用于补充原文依据；相似匹配用于历史过程参考。
- 建立问题类型和工具链路的初始映射。

验收标准：

- 能说清每类问题应优先走哪条链路。
- 已有代码中可复用模块被识别出来，不重复造同类能力。
- 明确统计类问题不能依赖 `top_k chunk`。

## 阶段 1：意图识别

阶段 1 负责把用户一句话拆成业务意图和结构化槽位。一个问题可以同时命中多个意图，例如“当前山西北部强对流像哪些历史过程，要重点关注什么”同时包含相似个例和服务决策。

核心工作：

- 规则链路扫描关键词，例如“多少”“对比”“雷达图”“受灾最严重”。
- 槽位提取时间、月份、灾种、地区、图片类型等字段。
- 上下文链路预留对话状态能力，后续可结合多轮问题。
- 安全链路单独判断是否涉及写操作、删除、重建、上传等风险。

验收标准：

- 常见问题能识别到正确主意图。
- 混合问题能保留多个意图，而不是只取一个。
- 意图结果中包含可解释原因，便于调试。
- 风险提示不影响只读问答，但能进入审计信息。

## 阶段 2：工具匹配和执行计划

阶段 2 负责根据意图选择工具，并生成清晰的执行计划。它不直接回答问题，只决定后续应该调用哪些能力。

核心工具路线：

- `standard_cases_filter`：按时间、灾种、地区筛选标准化个例。
- `standard_cases_aggregate`：对标准化个例做全量聚合统计。
- `image_metadata_search`：检索雷达图、卫星云图、降水图等图片证据。
- `document_chunk_retrieve`：补充原文 chunk 证据。
- `similar_case_match`：匹配相似历史个例。
- `answer_synthesis`：组织最终回答。

验收标准：

- 统计汇总类问题必须包含 `standard_cases_aggregate`，并禁止 `top_k_chunk_retrieve` 作为主链路。
- 证据检索类问题命中图片条件时必须包含 `image_metadata_search`。
- 相似个例和服务提示类问题必须包含 `similar_case_match`。
- 执行计划能返回给前端或调试面板查看。

## 阶段 3：结构化执行和证据组织

阶段 3 负责真正执行计划中的只读查询，并把结果整理成统一结构。这个阶段强调“先用结构化数据回答能确定的问题”，避免所有问题都落到文档片段检索。

典型链路：

- 统计汇总：从 `standard_cases` 全量过滤，再按月份、灾种、地市聚合。
- 对比分析：按月份或灾种分组，输出差异、共性和代表个例。
- 单过程复盘：定位标准化个例，再补充图片或原文证据。
- 证据检索：按图片类型和个例条件筛选，返回可追溯图像证据。
- 缺口判断：如果缺少灾情数据、图片证据或标准化个例，明确说明。

验收标准：

- 结构化问题优先返回 `structured_cases:*` 或 `agent:*` 结果。
- 统计数字可追溯到标准化个例集合。
- 图片证据能关联来源 PDF、页码、图注或图片 ID。
- 找不到证据时返回“缺失”或“不能判断”，不编造。

## 阶段 4：回答合成器

阶段 4 负责把执行结果变成用户能直接阅读的自然语言回答。这一阶段要避免把检索过程、内部条件或片段堆叠暴露给用户。

回答原则：

- 先正面回答用户问题，再展开依据。
- 主回答不输出“检索条件”这类内部过程。
- 不使用“可以先从已命中的材料看出”这类自言自语模板。
- 统计、对比、复盘类回答尽量采用“结论 / 结构化事实 / 检索证据 / 模型分析 / 缺口”的结构。
- 对服务提示类问题，先给关注重点，再列相似历史过程。

验收标准：

- 回答正中问题，不只列数据。
- 结构清晰，语言简洁，用户能直接拿去看。
- 证据和分析分开，避免把推断写成事实。
- 没有证据时明确说证据不足。
- fallback 回答也要像人话，而不是 raw chunk 摘要。

## 阶段 5：多 agent 化增强

阶段 5 把意图识别、工具判断、安全审查、结构化执行、相似匹配和回答合成拆成可替换模块。这里的“多 agent”更强调工程边界，而不是一定要启动多个独立进程。

推荐模块：

- `intent_analyzer`：负责意图和槽位。
- `planner`：负责工具选择和执行计划。
- `structured_answerer`：负责标准化个例统计、对比、复盘和证据检索。
- `similar_case_matcher`：负责相似历史过程。
- `document_retriever`：负责文档 chunk 兜底证据。
- `answer_synthesizer`：负责最终表达。
- `safety_checker`：负责权限和风险判断，可继续增强。

统一输入输出要求：

- 每个子模块接收明确输入，例如 `question`、`slots`、`cases`、`history`。
- 每个子模块返回结构化结果，例如 `status`、`reason`、`evidence`、`failures`。
- 单个子模块失败时，主调度器能降级，不影响整体回答。
- 后续接 MCP 或外部工具时，只需要替换某个模块，不改变整体协议。

验收标准：

- 主调度器可以并行或准并行地合并多个链路结果。
- 每个子 agent 有统一的状态记录。
- 子 agent 失败会进入 `audit.failures`。
- 失败后能降级到其他可用证据链路。

## 阶段 6：线上评估和审计

阶段 6 负责让系统可观测、可评估、可回流。智能体回答质量不是一次性写完，而是要通过真实问题持续迭代。

核心能力：

- 日志：记录问题、意图、计划、执行工具、失败链路和最终回答。
- 调试视图：前端展示“智能体链路”，能看到每个子模块的状态。
- 失败样本回流：把答非所问、证据不足、链路选错的问题加入评测集。
- 线上评估：用固定问题集定期检查回答是否正中问题、结构清晰、语言简洁、易于理解。

验收标准：

- 每次问答能看到识别了什么意图、为什么、用了哪些工具、跳过了哪些工具。
- 失败问题可以沉淀为回归测试或评测样本。
- 新增能力不会破坏已有 20 问验收集。
- 后端测试和前端构建能作为发布前基本门槛。

## 当前已覆盖的典型问题

| 问题类型 | 示例 | 推荐链路 |
| --- | --- | --- |
| 证据检索 | 5月21-22日过程有哪些雷达图？ | 标准化个例定位 + 图片元数据 |
| 单过程复盘 | 请分析5月21-22日暴雨过程 | 标准化个例定位 + 图片/原文补证 |
| 统计汇总 | 5-7月有多少个灾害天气过程？ | `standard_cases` 全量过滤 + 聚合 |
| 对比分析 | 6月和7月强对流过程有什么差异？ | 分组筛选 + 聚合对比 + 代表个例 |
| 相似个例 | 当前山西北部强对流像哪些历史过程？ | 相似匹配 + 典型证据 |
| 服务提示 | 今天这个过程要重点关注什么？ | 当前条件 + 相似个例 + 经验提示 |
| 数据缺口 | 没有灾情数据能判断受灾最严重吗？ | 证据边界判断 + 缺口说明 |

## 质量底线

系统回答必须满足四个基本标准：

- 正中问题：先回答用户真正问的是什么。
- 结构清晰：事实、证据、分析和缺口分开。
- 语言简洁：不输出内部检索条件，不堆砌无关片段。
- 易于理解：用气象业务人员能直接读懂的表达。

如果一个回答只是列出命中数量、检索条件或原文片段，而没有给出结论和判断口径，就应视为失败样本，进入下一轮评测和修正。
