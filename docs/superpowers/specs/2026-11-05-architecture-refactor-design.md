# 气象灾害个例智能分析系统架构规整设计

## 1. 背景

当前系统已经形成以统一会话聊天为主入口的业务形态，但代码在持续迭代中出现了职责混杂、目录命名不统一、Router 分散、全局状态隐式依赖和运行产物进入版本库等问题。本次工作只调整结构、依赖关系和可维护性，不改变现有业务规则、公开接口协议和用户可见功能。

本设计基于方案 A：保留现有查询 URL，在内部统一到一个主查询业务服务，实现渐进式兼容重构。

## 2. 目标

1. 将 `runtime/`、`logs/`、测试输出、截图、数据库和 `.codex_tmp/` 移出 Git 跟踪，并完善 `.gitignore`。
2. 保留 `/api/query`、`/api/agent/query`、`/api/query/stream` 三个公开查询 URL，让三个入口共享同一套查询业务服务。
3. 将 `main.py` 中的业务逻辑抽出，引入依赖注入，消除 Router 和统一编排器对 `main` 的反向依赖。
4. 将 `Smart_Case_Match` 统一为 `smart_case_match`，将 `query-intent-agent` 统一为 `query_intent`。
5. 将所有 Router 集中到 API 层，业务包只保留领域逻辑和服务实现。
6. 拆分承担过多职责的编排函数、前端大组件和过宽异常处理。
7. 按职责移动测试，测试源码与测试运行产物分开管理。
8. 以现有代码为依据更新 `README.md`，使文档结构与重构后的项目一致。

## 3. 非目标

- 不配置 Ruff、Mypy、ESLint、Prettier 或 CI。
- 不改变前端页面布局、交互方式、公开接口 URL、SSE 事件名、核心响应字段和业务规则。
- 不重新设计模型提示词、检索算法、排序规则、报告格式或数据模型。
- 不为了满足行数指标压缩代码、删除必要注释或制造职责零碎的文件。
- 不删除用户本地已有的运行数据、日志、数据库、截图和测试输出。

## 4. 当前主要问题

### 4.1 应用入口职责过多

`backend/app/main.py` 同时负责应用创建、全局客户端初始化、知识库服务、查询业务、结果转换和 Router 注册，导致应用装配与业务实现无法独立理解和测试。

### 4.2 反向依赖与隐式全局状态

多个 Router 通过延迟导入 `backend.app.main` 获取服务，统一编排器也直接读取 `main` 模块中的私有函数。这形成 Router、编排器对应用入口的反向依赖，并让测试和替换实现变得困难。

### 4.3 查询链路重复

三个查询入口分别访问若干 `main` 私有函数，缺少统一的服务边界。旧接口虽然需要继续兼容，但不应继续维护一套独立业务实现。

### 4.4 目录职责不清

业务包中直接放置 Router、运行产物和演示页面，命名同时存在下划线、驼峰和连字符形式，导致导入路径和部署行为受操作系统与 Python 包规则影响。

### 4.5 文件规模过大

统一编排器、若干 Agent 实现、查询服务及前端组件体量较大，单文件存在多个业务阶段、状态转换和异常分支，影响局部修改与测试定位。

### 4.6 运行产物进入版本库

历史运行生成的文件、日志、截图、数据库、缓存和测试诊断结果被 Git 跟踪，既扩大仓库，又容易造成环境间污染。

## 5. 应用架构

### 5.1 应用工厂

`backend/app/main.py` 最终只保留应用装配职责：

```text
main.py
  └── create_app()
        ├── 注册 lifespan
        ├── 配置 CORS
        └── 注册 api/routes 下的全部 Router
```

模块导入时不得连接数据库、加载模型、创建目录或执行业务任务。目录创建、连接初始化和服务实例化由 lifespan 完成。

### 5.2 组合根与依赖注入

新增 `backend/app/services/container.py`，由其中的 `AppServices` 负责构造和持有应用级服务。`AppServices` 是组合根，不承载业务流程。

服务容器计划包含：

- 配置对象。
- 模型客户端。
- 文档存储、标准化个例存储、图片证据库和会话存储。
- 文档问答、结构化问答和知识库构建服务。
- 统一查询服务。
- 多维个例 Agent 和 Smart 相似个例 Agent。
- 意图识别与规划能力。

FastAPI lifespan 负责创建并关闭 `AppServices`。Router 通过 `backend/app/api/dependencies.py` 提供的依赖函数获取服务，不得导入 `main`。

业务服务通过构造函数接收所需依赖。编排器接收明确的服务接口，不接收整个应用入口模块，也不调用另一个模块的私有函数。

### 5.3 分层边界

- API 层负责接收参数、执行请求级校验、调用业务服务和返回响应。
- 业务服务层负责查询意图、链路选择、业务规则和结果组装。
- Agent 层负责各领域分析、检索、生成和流式输出。
- 数据访问层负责 SQLite、ChromaDB、JSON 索引和文件存储。
- 集成层负责模型服务、重排序服务及其他外部接口。

API 层不得包含检索算法和提示词业务；数据访问层不得依赖 FastAPI；业务包不得注册 Router。

## 6. 统一查询业务链路

### 6.1 对外接口

保留以下 URL 和现有响应协议：

```text
POST /api/query
POST /api/agent/query
POST /api/query/stream
```

`/api/query/stream` 是前端唯一主业务链路。`/api/query` 和 `/api/agent/query` 是兼容适配器，继续服务已有调用方。

### 6.2 内部链路

```text
POST /api/query
POST /api/agent/query       -> ChatService 兼容方法
POST /api/query/stream      -> ChatService 流式方法
                                   |
                                   v
                         UnifiedChatOrchestrator
                           |        |         |
                           v        v         v
                       文档问答   多维个例   Smart 匹配
```

三个入口共享以下能力：

- 会话存在性校验与会话消息读取。
- 上下文个例和对话历史提取。
- 结构化问题识别。
- 文档问答、多维检索和 Smart 匹配选择。
- 图片、图表、证据和运行审计信息组装。
- 会话消息写入与会话记忆元数据生成。
- 查询响应转换。

兼容接口可以使用同步适配方法，统一入口使用异步流式方法，但两者调用相同的业务组件，不复制查询实现。

### 6.3 编排器依赖

`UnifiedChatOrchestrator` 不再接收 `main` 模块对象。它接收明确依赖：

- 统一查询服务或文档问答服务。
- 多维个例 Agent。
- 多维会话存储适配器。
- Smart 相似个例 Agent。
- 意图识别服务。
- 会话存储。
- 配置与时钟等基础设施依赖。

公开 `stream()` 方法的方法名、参数结构和产出事件协议保持不变。

### 7.1 Router 迁移

以下 Router 从业务包移到 API 层：

- `case_multidim_search/router.py` -> `api/routes/case_multidim.py`
- `Smart_Case_Match/router.py` -> `api/routes/smart_case_match.py`
- `query-intent-agent/router.py` -> `api/routes/query_intent.py`

现有 `api/routes/agent.py`、`sessions.py`、`system.py`、`vectors.py` 保留在 API 层，但改为依赖注入。

迁移时保留原路由前缀、HTTP 方法、参数模型、响应模型和静态资源地址。

### 7.2 命名统一

- `Smart_Case_Match` 改为 `smart_case_match`。
- `query-intent-agent` 改为 `query_intent`。
- 删除不再需要的 `query_intent_compat.py` 动态导入兼容层。
- Python 包、模块、函数和变量使用 snake_case；类使用 PascalCase；常量使用 UPPER_SNAKE_CASE。

### 7.3 测试目录

`backend/tests/` 分为：

- `unit/`：纯函数、解析、排序、状态转换和局部服务。
- `integration/`：Router、存储、服务和模型客户端边界。
- `e2e/`：统一流式入口、会话链路和跨模块行为。

固定测试代码进入测试目录；测试运行产生的 JSON、日志、PNG 和其他诊断文件不进入 Git。

## 8. 运行产物与版本控制

### 8.1 移出 Git 跟踪

使用 `git rm --cached` 将以下已跟踪内容移出版本控制，同时保留工作区文件：

- 各业务包下的 `runtime/`。
- 各业务包下的 `logs/`。
- `.codex_tmp/`。
- 数据库文件。
- 测试输出、诊断 JSON 和运行截图。
- README 引用的本地演示截图 `tmp/img*.png`。

固定测试源码、配置示例和必要的小型数据清单不视为运行产物；是否保留以文件职责为准。

### 8.2 `.gitignore`

新增明确规则覆盖：

- `runtime/` 与 `logs/` 目录。
- `.codex_tmp/`。
- 测试输出目录、诊断 JSON 和测试截图。
- SQLite 数据库及其临时文件。
- Numba 缓存和运行时缓存。
- Python、前端和测试工具产生的临时产物。

忽略规则按“环境与缓存、运行数据、测试产物、构建产物”分组并添加中文注释。

### 8.3 数据路径

运行时数据根目录通过现有配置体系解析。代码不得在业务包内拼接固定运行目录。

目录创建放到应用启动阶段。测试通过临时目录或依赖覆盖隔离写入，不修改仓库内数据。

## 9. 配置与硬编码

- API Key、服务地址、端口、模型名和数据路径继续通过环境变量和配置对象读取。
- 具有业务含义的固定阈值和状态值使用具名常量。
- 稳定的局部字面量可以保留，不进行无意义的全局配置化。
- 配置模块导入时不创建目录，也不执行需要外部连接的初始化。
- 禁止把真实密钥写入代码、示例、日志或 Git。

## 10. 代码拆分要求

### 10.1 后端

- 新建 Python 文件原则上以 100～300 行为宜，预计超过 400 行时先按职责判断是否需要拆分。
- 单个函数尽量控制在 20～50 行，超过 80 行时检查职责和可测试性。
- 已有超大文件只拆分本次直接涉及的职责，不进行与目标无关的全仓机械重写。
- 公共函数和核心业务函数提供参数与返回值类型标注，避免不必要的 `Any`。
- 固定结构的数据优先复用现有 Pydantic 模型、dataclass 或 TypedDict。
- 函数避免布尔参数控制完全不同的业务行为，避免可变默认参数。

`UnifiedChatOrchestrator` 按以下职责拆分：

- 会话上下文和依赖解析。
- 任务规划与链路选择。
- 文档问答执行。
- 多维个例执行。
- Smart 相似个例执行。
- 进度事件和流式增量转换。
- 最终结果保存与会话元数据组装。

公开入口保留在协调模块中，内部执行模块不互相反向依赖。

### 10.2 前端

`ChatPanel.vue` 按职责拆分为输入区、消息区、证据与预览区和流式状态处理。`AssistantMessageActions.vue` 按交互职责拆分为操作栏和反馈/版本处理。

拆分后保持现有组件对外 props、事件和页面行为不变。共享状态通过组合函数或明确的子组件 props 传递，不引入全局可变状态。

### 10.3 异常处理

- 移除无差别吞掉所有异常的宽泛处理。
- 模型、网络、文件、数据库和 SSE 分别处理可预期异常。
- 编程错误不得伪装成普通业务失败，应保留堆栈并交给统一错误处理。
- API 边界将领域异常映射为现有 HTTP 状态码和响应格式。
- 日志记录异常类型、业务上下文和必要的非敏感标识，不记录密钥和完整敏感请求。

## 11. 兼容与行为约束

- 保留三个查询 URL、请求字段、响应字段和 SSE 数据前缀。
- 保留前端 API 调用路径和事件解析方式。
- 保留现有会话、消息、报告、反馈、分享、版本和导出行为。
- 保留现有 Agent 选择和业务判定规则。
- 目录移动只改变内部导入路径，不改部署时的公开 URL。
- 如测试暴露历史行为依赖，优先增加适配而不是修改前端契约。

## 12. 测试与验证

### 12.1 自动化验证

依次执行：

1. Python 全量编译检查。
2. 后端应用导入和 Router 注册检查。
3. 后端现有单元与集成测试。
4. 查询兼容接口测试。
5. SSE 统一入口事件冒烟测试。
6. 前端依赖安装检查和生产构建。

当前系统 Python 环境缺少 FastAPI、OpenAI、ChromaDB、Uvicorn、Pytest 和 SQLAlchemy。验证前创建项目虚拟环境并按 `requirements.txt` 安装依赖。网络受限时再发起明确权限确认。

### 12.2 双端口启动验证

1. 在 `8000` 端口启动 FastAPI 后端。
2. 在 `5173` 端口启动 Vite 前端。
3. 检查 `/api/health` 和 `/api/knowledge/status`。
4. 打开前端页面，确认资源加载和会话列表正常。
5. 通过 `/api/query/stream` 发起不依赖外部模型的轻量请求，确认 SSE 能建立并收到结构化错误或正常事件。
6. 在完成后关闭两个测试进程。

### 12.3 回归重点

- 三个查询 URL 仍可访问。
- Router 不再导入 `main`。
- 编排器不再持有 `main` 模块。

- Router 只在 `api/routes` 注册。
- 运行数据写入配置指定的目录，不写入 Git 跟踪目录。
- README 命令与新目录和启动方式一致。

1. `main.py` 不再包含查询、检索、报告和会话业务实现。
2. Router 和编排器不再直接或间接依赖 `main`。
3. 三个查询入口共享同一个查询业务服务。
4. `smart_case_match` 和 `query_intent` 命名及导入正常。
5. 所有 Router 位于 API 层。
6. 指定运行产物不再被 Git 跟踪，`.gitignore` 能阻止同类产物再次入库。
7. 后端可导入并启动，前端可构建并启动。
8. 健康检查、页面加载、统一 SSE 和现有测试通过，或对无法执行的外部模型场景给出明确验证结果。
9. 公开接口协议和现有业务行为没有非预期变化。
10. README 与最新代码结构和启动方式一致。

## 15. 风险与控制

- 目录改名可能影响深层导入：通过全仓搜索、编译和测试逐项消除旧引用。
- Router 迁移可能影响生命周期：所有单例由 `AppServices` 统一创建和关闭。
- 查询统一可能改变细微响应差异：先为现有协议补充特征测试，再替换内部实现。
- 超大文件拆分可能引入循环依赖：先抽稳定数据模型和接口，按“API -> 业务 -> Agent -> 数据访问”方向组织依赖。
- 运行产物移出跟踪会缩短 Git 历史中的可见数据，但不会删除本地文件；README 远端截图失效作为已确认影响记录。
- 依赖缺失可能阻塞完整测试：先完成静态检查和前端构建，再在获批环境中安装依赖并执行双端口验证。
