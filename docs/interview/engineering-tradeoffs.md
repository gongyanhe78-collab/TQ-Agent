# 工程取舍说明

> 本文档回答三个高频面试问题：为什么采用模块化单体、为什么暂不引入
> Kafka/Kubernetes、为什么 Redis 不是长期记忆主库。所有文档与注释使用中文。

## 1. 为什么采用模块化单体

- 项目当前是单机演示与开发环境，用户量与数据规模有限，单体足以承载全部流量，
  部署、调试和故障定位成本最低。
- 业务内聚度高：会话、意图路由、RAG 检索、报告生成共享同一进程内的事务边界，
  拆成微服务反而要引入跨服务事务与网络重试，收益不抵成本。
- 模块化体现在包边界与依赖方向：`api/routes` 只做协议层，`services` 做组合根，
  `db` 做持久化，`observability` 统一日志与指标。后续需要拆分时，可以按这些
  边界逐步独立，不必推翻现有代码。

## 2. 为什么暂不引入 Kafka 与 Kubernetes

- Kafka 解决的是高吞吐异步消息与多消费者问题，当前系统没有跨服务事件总线的需求；
  用数据库状态机（运行记录 + 状态字段）即可表达任务进度与失败重放。
- Kubernetes 解决的是多副本调度、滚动发布与弹性伸缩；单机场景下 Docker Compose
  的依赖健康检查与命名卷已经覆盖启动顺序与数据持久化需求。
- 引入这两个组件会显著增加运维复杂度（存储、网络、认证），而当前收益为零，
  属于“为了企业化而堆组件”的反模式。

## 3. 为什么 Redis 不是长期记忆主库

- Redis 是内存数据库，容量有限且重启即丢数据，无法承担权威事实存储。
- 本项目采用“先写 PostgreSQL 成功、再刷新 Redis”的写入顺序，Redis 只作为可重建
  的短期上下文加速层；Redis 数据丢失后从 PostgreSQL 自动回填，不影响历史会话。
- 长期记忆（用户记忆摘要）同样以 PostgreSQL 为事实源，Redis 只缓存最近访问，
  避免出现“缓存即真相”导致的历史不可恢复。

## 4. 数据与向量库的迁移边界

- SQLite → PostgreSQL：PostgreSQL 成为权威数据源后，SQLite 只保留迁移前的只读
  备份；迁移脚本提供 dry-run 与行数对账，保证可重复执行。
- Chroma → Milvus：检索索引不是唯一事实，任何时刻都可以从 PostgreSQL/JSON 权威
  数据重构建；切换有开关、有基线对比、有回退路径，不会在没有基准的情况下直接
  删除旧后端。
