## 1. 背景与现状

### 1.1 为什么需要这份方案

系统已经具备两套评测能力：

- **离线固定夹具**：不调用模型，只验证 Harness、指标计算和报告链路是否稳定；
- **真实模型执行（`--real`）**：调用真实意图模型、向量模型、重排模型和 Milvus 混合检索。

离线固定夹具的数值（路由 8.33%、hit@1 11.67%）只能证明“管线能跑”，不能代表系统效果。
真实模型实测虽然明显更高，但仍有多个指标偏低。本方案用于回答三个问题：

1. 每个指标到底在衡量什么；
2. 当前分数低，低在哪里；
3. 按什么顺序、用什么手段提升，如何验收。

## 2. 指标口径详解

### 2.1 证据序列的定义

单条样例的“实际证据序列”按以下顺序拼接：

```text
actual_evidence = actual_case_ids + actual_chunk_ids
expected_evidence = expected_case_ids + expected_chunk_ids
```

个例 ID（case）在前，文档切片 ID（chunk）在后。**顺序会直接影响 hit@k 和 MRR**，
因此“个例 ID 是否应该计入 RAG 样例的证据序列”本身就是一个需要明确的口径问题。

### 2.2 路由类指标

#### route_accuracy（路由准确率）

- **含义**：系统把问题分发给哪个 Agent，是否与人工期望一致。
- **计算**：实际路由与期望路由完全相等记 1，否则记 0；60 条取平均。
- **取值**：`rag`、`multidim_search`、`similar_case_match`、`clarify`。
- **当前值**：45.00%（33/60 条不一致）。
- **注意**：这是“分发决策正确率”，不是“答案正确率”。路由错但答案对，此项仍记为 0。

### 2.3 检索类指标

#### hit_at_1（首位命中）

- **含义**：返回的第 1 条证据是否命中任意一条期望证据。
- **计算**：`前 1 条与期望集合有交集 → 1，否则 0`。
- **当前值**：50.00%。
- **解读**：一半样例的第一条证据就是正确的，最能反映重排质量。

#### hit_at_3（前三命中）

- **含义**：前 3 条证据中是否命中任意一条期望证据。
- **计算**：`前 3 条与期望集合有交集 → 1，否则 0`。
- **当前值**：66.67%。
- **解读**：比 hit@1 高 16.67 个百分点，说明不少正确证据排在第 2~3 位。

#### recall_at_5（前五召回）

- **含义**：前 5 条证据覆盖了多大比例的期望证据。
- **计算**：`命中数 / 期望证据总数`，再对 60 条取平均。
- **当前值**：43.06%。
- **关键提醒**：40/60 条样例有多个期望证据（多个 case 或多个 chunk），
  在固定只取 5 条的前提下，这个指标天然偏低，不能与 hit@1 直接比较。

#### mrr（平均倒数排名）

- **含义**：第一个正确证据排得有多靠前。
- **计算**：`1 / 首个命中的排名`，无命中记 0，再取平均。
- **当前值**：58.17%。
- **解读**：约等于正确证据平均排在第 1.7 位。

#### evidence_id_hit_rate（证据命中率）

- **含义**：是否至少命中一条期望证据。
- **计算**：`实际证据集合与期望集合有交集 → 1，否则 0`。
- **当前值**：75.00%（45/60 条至少命中一条）。
- **解读**：这是“召回有没有方向性错误”的粗粒度指标。

#### no_result_accuracy（无结果准确率）

- **含义**：该返回空结果时返回空结果，不该返回时不要返回空。
- **计算**：`预测无结果 == 期望无结果 → 1`。
- **当前值**：88.33%（7 条判断错误）。

### 2.4 回答质量类指标

#### required_fact_coverage（必含事实覆盖率）

- **含义**：回答覆盖了多少条人工标注的“必含事实”。
- **计算**：对每条 fact 做**归一化后的子串匹配**：
  - 统一全角/半角；
  - `℃`、`°C`、`摄氏度` 视为同一写法；
  - 忽略空白；
  - 支持 `A|B` 形式的“任选其一”。
- **当前值**：11.67%。
- **关键提醒**：这是当前**最需要治理**的指标，原因见 3.4 节。

#### citation_support_rate（引用支持率）

- **含义**：回答中引用的证据 ID，是否都能在本次检索结果中找到依据。
- **计算**：`有支撑的引用数 / 总引用数`；没有引用时记 1。
- **当前值**：100%。
- **解读**：说明回答没有编造检索结果之外的引用。

#### forbidden_claim_count（违规断言数）

- **含义**：回答中出现了多少条明令禁止的结论。
- **计算**：完整禁止短语出现次数求和（归一化后匹配）。
- **当前值**：0。
- **解读**：0 是期望值，说明没有越界结论。

#### abstention_accuracy（拒答准确率）

- **含义**：该拒答时拒答、不该拒答时不拒答。
- **计算**：`预测拒答 == 期望拒答 → 1`。
- **当前值**：88.33%（7 条判断错误，与 no_result 基本同源）。

### 2.5 指标的整体局限

1. **部分指标依赖证据顺序**：hit@k、MRR 对 `case_ids` 与 `chunk_ids` 的排列敏感。
2. **recall@5 对多证据样例不友好**：固定 5 条无法覆盖大量期望证据。
3. **required_fact_coverage 依赖标注质量**：标注写的是“行为期望”时，子串匹配必然失败。
4. **真实模型评测有随机性**：temperature=0.3、模型服务状态都会影响结果，应多次取均值。

## 3. 实测数据分析

### 3.1 分类表现

| 类别 | 样例数 | 路由准确率 | 首位命中 | 必含事实覆盖 |
|------|-------:|-----------:|---------:|-------------:|
| 路由 | 6 | 33.33% | 16.67% | 0.00% |
| 检索 | 12 | 25.00% | 66.67% | 0.00% |
| 统计 | 8 | 87.50% | 87.50% | 22.92% |
| RAG | 10 | 100.00% | 80.00% | 51.67% |
| 相似匹配 | 8 | 0.00% | 37.50% | 0.00% |
| 多轮记忆 | 10 | 30.00% | 30.00% | 0.00% |
| 故障场景 | 6 | 33.33% | 0.00% | 0.00% |

**观察**：

- RAG 类路由 100%、首位命中 80%，说明文档问答主链路最成熟；
- 相似匹配路由 0%、多轮记忆路由 30%，是路由层的主要短板；
- 检索类首位命中 66.67% 但路由仅 25%，说明“检索能力本身尚可，分发出了问题”。

### 3.2 路由错配分布

33 条错配的分布如下：

| 期望路由 | 实际路由 | 条数 |
|----------|----------|-----:|
| multidim_search | rag | 17 |
| similar_case_match | rag | 10 |
| clarify | rag | 2 |
| clarify | similar_case_match | 1 |
| similar_case_match | clarify | 1 |
| clarify | 空串 | 1 |
| multidim_search | similar_case_match | 1 |

**结论**：27/33 条错配集中在“多维检索/相似匹配被分到 RAG”。
根因是当前生产规则把“对库内已有个例做统计或列举”优先交给主 RAG，
而黄金数据集按早期契约期望 `multidim_search`。这属于**路由契约差异**，不是检索失败。

### 3.3 检索瓶颈

- 证据命中率 75%，说明 45/60 条能找到至少一条正确证据；
- 但 40/60 条是多证据样例，其 recall@5 平均仅 **32.08%**；
- 固定 `top_n=5` 对多证据问题明显不够。

**结论**：检索的主要问题不是“找不到”，而是“找不全、排不齐”。

### 3.4 回答瓶颈

- 证据命中的 45 条样例中，required_fact_coverage 平均只有 **15.56%**；
- 33/60 条样例的 `required_facts` 写的是行为期望（以“应”开头），
  例如“应同时覆盖6月和7月的强对流过程”“应先澄清时间、区域或灾种”；
- 这类文本不会逐字出现在回答里，子串匹配必然为 0。

**结论**：事实覆盖率低有两层原因：

1. **标注口径问题**（33 条，占 55%）；
2. **回答生成没有系统性覆盖结构化事实**（即使证据命中，覆盖率也只有 15.56%）。

### 3.5 稳定性瓶颈

- 本次运行出现 17 次意图模型 `Request timed out`，回退到确定性规则路由；
- p50 延迟 36.3 秒、p90 延迟 55.9 秒，主要耗时在意图理解和回答生成；
- 高并发（`max_concurrency=4`）会加剧超时。

**结论**：路由准确率有一部分损失来自模型超时，而不是规则本身。

## 4. 优化目标

### 4.1 分阶段目标

| 指标 | 当前 | 阶段 A 目标 | 阶段 B 目标 | 阶段 C 目标 |
|------|-----:|------------:|------------:|------------:|
| route_accuracy | 45.00% | ≥ 70% | ≥ 75% | ≥ 80% |
| hit_at_1 | 50.00% | 50% | ≥ 60% | ≥ 65% |
| hit_at_3 | 66.67% | 67% | ≥ 75% | ≥ 80% |
| recall_at_5 | 43.06% | 43% | ≥ 60% | ≥ 65% |
| mrr | 58.17% | 58% | ≥ 65% | ≥ 70% |
| evidence_id_hit_rate | 75.00% | 75% | ≥ 85% | ≥ 88% |
| required_fact_coverage | 11.67% | ≥ 50% | ≥ 55% | ≥ 65% |
| citation_support_rate | 100% | 100% | 100% | 100% |
| forbidden_claim_count | 0 | 0 | 0 | 0 |
| abstention_accuracy | 88.33% | ≥ 95% | ≥ 95% | ≥ 95% |

> 说明：阶段 A 的 required_fact_coverage 提升主要来自“标注口径治理”，
> 属于“把指标测准”，不是模型能力突变；阶段 C 的提升才来自回答生成优化。

### 4.2 目标设定原则

1. **先测准，再优化**：口径不一致时，任何提升都不可信；
2. **分指标设目标**：路由、检索、回答分别验收，不混在一起；
3. **保留安全底线**：citation_support_rate 必须保持 100%，forbidden_claim_count 必须为 0；
4. **真实模型与离线夹具分开看**：离线夹具只做回归门禁，不做质量目标。

## 5. 优化方案

### P0-1 统一路由契约（收益最大）

**问题**：27/33 条路由错配来自“多维检索/相似匹配 → RAG”的契约差异。

**可选方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| A（推荐） | 承认“库内统计/列举由主 RAG + 结构化问答完成”是正确产品行为，更新黄金数据集的路由期望 | 改动小、与现网一致、风险低 | 需要同步更新数据集契约文档 |
| B | 修改意图规则，让“统计/检索/列举 + 库内个例”优先走 `multidim_search` | 保留原数据集契约 | 会影响现网行为，需要完整回归 |

**推荐 A 的理由**：

- 现网主 RAG 内部已经能调用结构化问答，功能上并不缺能力；
- 改规则（方案 B）会影响所有线上问题分发，回归成本高；
- 评测应度量“产品定义的正确行为”，而不是固守早期实现。

**预期收益**：route_accuracy 从 45% 提升到 **75%~85%**。

**验证方式**：

1. 在契约文档中写明三类路由的边界；
2. 对 33 条错配样例逐条确认新期望；
3. 重跑真实评测，确认 route_accuracy ≥ 70%。

**风险**：如果产品确实希望多维检索负责统计，则应选方案 B，不能为了方便改数据。

### P0-2 数据集事实标注治理

**问题**：33/60 条 `required_facts` 是行为期望，不是可逐字核验的事实文本。

**方案**：拆分字段。

```json
{
  "required_facts": [
    "平均气温为6.0摄氏度",
    "较常年同期偏高0.9摄氏度"
  ],
  "expected_behaviors": [
    "应先澄清时间、区域或灾种"
  ]
}
```

**字段定义**：

| 字段 | 含义 | 判定方式 |
|------|------|----------|
| `required_facts` | 回答中应逐字出现的事实（数值、站点、日期、数量） | 归一化子串匹配 |
| `expected_behaviors` | 行为期望（澄清、覆盖范围、比较方式） | 规则或 LLM-as-judge |

**执行步骤**：

1. 从 33 条行为型样例中提取可量化的部分写入 `required_facts`；
2. 其余行为描述迁入 `expected_behaviors`；
3. 为 `expected_behaviors` 设计独立指标（如行为满足率）；
4. 更新数据集清单与 SHA-256。

**预期收益**：required_fact_coverage 从 11.67% 提升到 **50%~70%**（属于“测准”收益）。

**风险**：重新标注必须由业务人员复核，不能由模型自动生成后直接采用。

### P1-1 动态证据窗口

**问题**：40/60 条样例是多证据，固定 top_n=5 覆盖不全。

**方案**：

- 根据解析出的个例数量动态调整：`top_n = clamp(期望个例数 × 2, 5, 10)`；
- 或按个例分组，每个个例至少保留 1~2 条最相关切片；
- 同时报告 recall@5 与 recall@10，避免单一窗口误导。

**预期收益**：recall@5 从 43.06% 提升到 **60%+**。

**验证方式**：对多证据样例单独统计 recall@5 / recall@10。

### P1-2 结构化事实注入回答

**问题**：证据命中的 45 条样例，事实覆盖平均只有 15.56%。

**方案**：

1. 回答上下文除文档切片外，加入 `standard_cases1.json` 的 `summary`、`weather_facts`；
2. Prompt 明确要求逐条回答数值、日期、站点、数量，不得省略；
3. 对“统计/汇总”类问题，优先使用结构化问答结果，再用模型组织语言。

**预期收益**：required_fact_coverage 提升 **15~25 个百分点**。

**风险**：结构化字段本身可能不完整，需要先做字段质量抽检。

### P1-3 相似匹配接入真实 Agent

**问题**：当前真实执行器的相似匹配只用结构化日期筛选，没有调用真实的相似度计算。

**方案**：

- `similar_case_match` 路由改为调用 `SmartCaseMatchAgent` 的真实匹配流程；
- 输出相似个例 ID、相似度与匹配理由；
- 把相似个例 ID 计入 `actual_case_ids`。

**预期收益**：相似匹配类 hit@1 从 37.5% 提升到 **60%+**。

### P1-4 多轮记忆增强

**问题**：多轮记忆类路由 30%、首位命中 30%、事实覆盖 0。

**方案**：

1. 把上一轮的 `case_ids`、查询条件、结果摘要注入 `memory_context`；
2. 对“继续/其中/刚才”等指代做显式解析；
3. 回答 prompt 中要求引用上一轮结果。

**预期收益**：多轮记忆类 hit@1 从 30% 提升到 **50%+**。

### P2-1 意图模型稳定性

**问题**：本次运行 17 次意图模型超时，回退规则路由。

**方案**：

- 真实评测并发从 4 降到 2；
- 意图模型超时从 60 秒调到 90 秒；
- 评估让意图模型也使用 `qwen3.7-flash`（通过 `DASHSCOPE_INTENT_MODEL` 配置）；
- 增加超时重试与熔断监控。

**预期收益**：路由回退次数显著下降，route_accuracy 提升 **5~10 个百分点**。

### P2-2 无结果与拒答判定规则化

**问题**：7 条 no_result / abstention 判断错误。

**方案**：

- 澄清路由 → 拒答；
- 无检索结果且回答含“未找到/无法确定/证据不足” → 拒答；
- 其余 → 不拒答；
- 对“预测未来”“读取他人数据”等越界问题统一走澄清。

**预期收益**：no_result_accuracy、abstention_accuracy 提升到 **95%+**。

### P2-3 CI 质量门禁

**方案**：

| 门禁 | 内容 | 是否阻塞合并 |
|------|------|--------------|
| 快速门禁 | 编译、Ruff、单元测试、前端构建 | 是 |
| 集成门禁 | PostgreSQL、Redis、鉴权、迁移、数据隔离 | 是 |
| 评测门禁 | 离线固定夹具 60 条 | 是 |
| 真实模型评测 | 定时/手动运行，记录趋势 | 否 |

**建议阈值（达到后再启用为阻塞项）**：

- route_accuracy ≥ 70%
- hit_at_1 ≥ 60%
- hit_at_3 ≥ 75%
- evidence_id_hit_rate ≥ 85%

## 7. 验收与度量规范

### 7.1 评测流程

1. **离线固定夹具**：每次提交必跑，验证 Harness 与指标计算；
2. **真实模型评测**：阶段结束或发版前运行，至少 2 次；
3. **人工抽检**：每阶段随机抽取 10 条失败样例，确认失败原因归类正确；
4. **报告归档**：结果写入 `docs/evals/`，包含模型配置、数据集版本、运行时间。

### 7.2 结果解读原则

- 离线固定夹具数值只能用于回归，不能用于对外宣传；
- 真实模型指标必须注明模型版本、并发、数据集 SHA；
- 路由、检索、回答三类指标分开汇报，不合并成单一“总分”；
- 任何指标提升都要能解释“是测准了，还是模型变强了”。

## 8. 风险与注意事项

| 风险 | 说明 | 应对 |
|------|------|------|
| 为了指标改期望值 | 会让分数虚高，失去评测意义 | 所有期望变更必须有契约文档与业务确认 |
| 真实评测随机性 | 模型输出、服务状态会波动 | 固定 temperature/seed，多次取均值 |
| 数据集过拟合 | 针对 60 条反复调参，泛化性下降 | 保留一部分样例不参与调优，作为留出集 |
| 结构化字段不完整 | 事实注入可能引入错误 | 注入前做字段质量抽检 |
| 并发导致超时 | 意图模型在高并发下不稳定 | 降低并发、增加超时、监控熔断 |
| 成本上升 | 宽召回 + 重排会增加调用量 | 控制 top_k、缓存、按需重排 |
