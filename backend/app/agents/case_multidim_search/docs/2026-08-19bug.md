# 2026-08-19 自然语言聊天式多维个例检索设计与实现记录

## 一、改造目标

在保留原结构化筛选页面和全部报告能力的前提下，新增一个纯自然语言聊天页面。用户不再通过复选框构造请求，而是用自然语言描述时间、灾种和影响区域；系统先把自然语言转换为 `StructuredCaseSearchRequest`，经用户确认后，再完整复用原有结构化检索、逐例分析、强度提取、图表、PDF 和 CSV 流程。

本次代码修改严格限定在 `backend/app/services/agent/case_multidim_search` 目录内。

## 二、核心设计原则

### 1. 自然语言只改变输入过程

自然语言入口不直接检索标准个例，也不另建报告生成流程。确认后的请求仍调用：

```text
CaseMultidimSearchAgent.analyze_structured(StructuredCaseSearchRequest)
```

因此下列逻辑与原结构化页面保持一致：

- 时间、灾种、地区的 AND/OR 检索语义；
- 当前个例 `source_chunk_ids` 的正式正文回查；
- 少于等于 6 个 chunk 全部使用，超过 6 个才 rerank；
- 强度指标提取和主要影响区域统计；
- 逐例大模型分析和规则降级；
- 图片筛选、统一图号和正文引用改写；
- 总体概况、分维度分析、结论和建议；
- 网页报告、PDF、CSV、进度和 answer 缓存。

### 2. 解析与执行分离

自然语言流程拆成两个明确阶段：

```text
POST /natural/parse
    只解析和展示最终结构化条件
    不执行检索
    不修改已确认上下文

POST /natural/search
    校验用户确认的 proposal_id
    原子写入已确认上下文
    调用原有 analyze_structured
```

这样可以避免一次误解析、用户尚未确认的输入或重复点击污染后续历史。

## 三、聊天上下文状态模型

每个聊天会话保存以下信息：

```json
{
  "conversation_id": "conversation_xxx",
  "version": 1,
  "committed_query": {},
  "pending": {},
  "history": []
}
```

字段含义：

- `committed_query`：最近一次用户已经确认并执行的查询，是后续追问唯一允许继承的上下文；
- `pending`：当前待确认条件卡，只用于页面确认，不能被下一轮继承；
- `version`：已确认上下文版本号，防止旧确认卡覆盖新上下文；
- `history`：保留最近的用户消息和确认事件，用于审计，不直接拼入模型提示词。

会话使用运行时 JSON 持久化，默认保留 7 天；待确认提案默认 30 分钟过期。写入采用临时文件替换方式，避免进程中断产生半个 JSON。

## 四、明确的上下文合并规则

### 1. 普通新消息：`new`

用户没有使用上下文操作词时，本轮作为全新检索，不继承上一轮条件。

例如已确认“2025年5月太原暴雨”，随后直接输入：

```text
查询6月大风过程
```

最终条件只有“6月、大风”，不会继续带上2025年、太原或暴雨。页面会明确提示“本轮按新检索处理，未继承上一轮已确认条件”。

### 2. “再限定”：`restrict`

保留上一轮没有被本轮提及的维度，本轮明确限定的维度替换为新的范围。

例如：

```text
上一轮：2025年1—5月，强对流/暴雨/冰雹，太原/晋中/吕梁
本轮：再限定太原和晋中
结果：2025年1—5月，强对流/暴雨/冰雹，太原/晋中
```

这里区域使用替换而不是简单追加，因为当前结构化检索同一维度为 OR；追加旧区域会扩大结果，与“限定”语义相反。

### 3. “只看”：`scope`

保留其他维度，只将本轮明确提及的维度收缩为指定值。

例如：

```text
上一轮：2025年5月，强对流/暴雨，太原
本轮：只看其中有冰雹的过程
结果：2025年5月，冰雹，太原
```

### 4. “改成”：`replace`

保留未提及维度，替换本轮明确修改的字段。时间维度继续按子字段处理：

- “把时间改成5月至7月”：保留已经明确的2025年，只替换月份；
- “把年份改成2024年”：保留已经明确的月份，只替换年份；
- 输入完整起止日期：整体使用精确日期，并清空快捷年份和月份。

### 5. 未确认提案隔离

如果上一轮“再限定太原和晋中”只完成解析但没有点击确认，下一条“把时间改成5月至7月”仍然从最近一次已确认条件派生，不会继承未确认的太原、晋中条件。

### 6. 陈旧确认卡保护

同一会话生成新提案后，旧提案立即失效。确认接口同时检查：

- `conversation_id` 是否存在；
- `proposal_id` 是否等于当前待确认提案；
- 提案是否超过 30 分钟；
- 提案的 `base_version` 是否等于当前已确认上下文版本。

任一不满足均返回 HTTP 409，要求用户重新解析，不能覆盖新上下文。

## 五、自然语言解析策略

### 1. 规则优先

当前规则直接识别：

- 带年份的精确日期和日期范围；
- 年份、年份范围、今年、去年；
- 单月、月份范围和跨年月份范围；
- 春、夏、秋、冬季；
- 18 个现有灾种；
- 山西 11 个地市；
- 晋北、晋中、晋南、山西北中南部、全省等业务区域。

灾种按长词优先匹配，避免“雷暴大风”同时重复解析成“雷暴”和“大风”。“山西”通常是报告范围背景，不自动作为区域过滤；“北部”单独出现时不会猜测，页面要求用户明确为“山西北部”或“晋北”。

### 2. 大模型仅补充

确定性规则没有识别出任何字段时，才尝试大模型补充。模型只能返回受控字段 JSON，且灾种、地市、区域必须同时满足：

- 位于本模块白名单；
- 对应文字确实出现在用户原始消息中。

模型不能猜测未表达的年份、灾种或地区。模型不可用时保留规则结果并提示用户补充条件。

### 3. 确认卡

每次检索前，页面必须分行展示：

```text
时间：……
灾种：……
地市：……
区域：……
```

同时展示本轮合并方式、修改摘要和解析警告。用户只有点击“确认并开始检索”后才会执行长耗时的逐例分析。

## 六、新增接口与页面

| 路径 | 作用 |
|---|---|
| `GET /api/case-multidim/natural-chat` | 自然语言聊天页面 |
| `POST /api/case-multidim/natural/parse` | 解析自然语言并生成待确认提案 |
| `POST /api/case-multidim/natural/search` | 确认提案并复用原结构化检索流程 |
| `POST /api/case-multidim/natural/reset` | 清除旧上下文并新建会话 |

聊天页面没有结构化复选框，包含：

- 用户和系统消息；
- 最终条件确认卡；
- 后端真实检索进度；
- 总体概况、强度汇总、分维度分析、统计图；
- 按主导灾种分组的逐例分析和证据图片；
- 综合结论、业务建议；
- 与每份报告绑定的 PDF 和 CSV 导出按钮。

每份报告的导出参数绑定在该报告自己的确认结果上，后续新提案不会导致旧报告导出错误轮次的数据。

## 七、异常和边界处理

- 没有识别到时间、灾种或地区时，确认按钮禁用；
- 首轮直接输入“再限定/只看/改成”时不执行，提示先建立完整查询；
- “北部”等不明确区域不自动猜测；
- 当前协议不支持排除条件，“不要暴雨”会提示改用“只看……”表达保留范围；
- 新建会话会清除服务端已确认上下文和浏览器当前会话引用；
- 会话编号只允许安全字符，防止路径穿越；
- 自然语言检索失败继续使用原进度和异常处理，不改变原结构化页面。

## 九、聊天报告卡片与同源 PDF 预览改造

### 1. 改造目标

自然语言聊天页不再把完整 HTML 报告直接铺在消息流中。检索完成后先显示一张 PDF 缩略卡，用户点击“查看”后在页面右侧打开完整报告，并支持展开、缩小、关闭和下载。

### 2. 所见即所得实现

本次没有在前端重新拼装另一份报告，而是继续复用现有 `PdfReportBuilder`：

1. 检索结果先保存为唯一的 `answer_id`；
2. 聊天页自动调用 `/api/case-multidim/export-pdf` 生成正式 PDF；
3. 前端把接口返回的 PDF Blob 保存为一个对象 URL；
4. 聊天卡片第一页缩略图、右侧完整预览和下载按钮全部引用该对象 URL；
5. 因为三个入口使用的是同一份二进制文件，所以不存在网页内容与下载 PDF 二次排版不一致的问题。

PDF 首页继续由统一构建器写入报告标题、生成日期和检索条件。检索条件按照日期、年份、月份、灾种、地市、区域逐行输出，只有实际存在的条件才展示。

### 3. 页面布局

- 默认状态下聊天区保持单栏，报告以轻量 PDF 卡片显示；
- 卡片包含文件名、生成日期、文件大小、第一页缩略预览、查看和下载按钮；
- 点击卡片后，桌面端左侧保留聊天，右侧展示完整 PDF；
- 展开按钮将 PDF 切换为整页宽度，缩小按钮恢复左右布局；
- 移动端使用覆盖式全屏预览，避免左右两栏过窄；
- 新建会话时关闭预览并释放当前页面创建的 PDF 对象 URL。

### 4. 强度汇总固定字段调整

“重点个例强度汇总”的第三列由“主要影响区域”改为“并发灾害”。并发灾害从标准个例的全部灾种中生成，自动排除本轮主导灾种和同义主导标签；没有其他灾种时显示“—”。结构化网页、报告数据和 PDF 使用同一个 `concurrent_disasters` 字段。

### 5. 自然语言上下文判定调整

上下文合并不再只依赖“再限定、只看、改成”三个固定词。当前策略为：

1. 明确的新建、补充、收缩或替换表达先由确定性规则处理；
2. 其余表达由大模型同时读取本轮消息和最近一次已确认结构化条件，判断 `new`、`restrict`、`scope` 或 `replace`；
3. 仅接受置信度不低于 0.72 的白名单操作；
4. 模型不可用或语义不确定时按新检索处理，不自动继承历史；
5. 未确认提案仍然不能进入 `committed_query`，旧确认卡版本保护保持不变；
6. “未继承上一轮”“未出现上下文操作词”等内部路由说明不再作为页面警告展示。

## 十、2026-08-20 性能流水线与单次逐例模型调用优化

### 1. 优化目标与并发边界

本次优化不是无上限增加模型请求，而是把个例处理改成有界业务流水线：准备池并发读取当前和后续个例的 chunk、整理证据、执行必要的 rerank 和读取图片元数据；已经准备完成的个例进入最多两路的生成池。模块级全局信号量再次限制生成式 LLM 最多并发两个，避免多个 HTTP 检索任务绕过单次请求内的并发设置。

所有异步结果都写回原始个例索引槽位，最终仍按检索排序和主导灾种分组顺序组装报告。图片连续编号只在全部个例归位后统一执行，因此任务完成先后不会改变网页与 PDF 的个例顺序、图片顺序或正文图号。

### 2. 每个个例只调用一次生成式大模型

旧流程分别调用“强度指标模型”和“个例分析模型”。新流程改为：

1. 读取该个例全部正式关联 chunk；
2. 恢复 PDF 强制换行并按完整句切分；
3. 收集所有含数字的完整证据句，以及“最大值出现在……”等必要承接句；
4. 超过六个 chunk 时 rerank 选择六个分析片段，不超过六个时全部保留；
5. 将“全部数字证据句 + 精选分析片段 + 图片元数据和图注”一次提交模型；
6. 模型一次返回 `metrics`、三段 `analysis` 和 `cited_image_ids`。

正式正文阶段只整理证据，不提前用规则决定极值，避免错误候选误导模型。后端仍严格校验每项指标的 `source_chunk_id`、`source_text`、指标白名单和单位；来源不属于当前个例或原句无法在正文核验时直接拒绝。提示协议明确范围端点、阈值与明确极值、国家站与区域站、降温与最低温度、降雪量与降水量及风速到风级换算规则。

### 3. 真正关闭思考模式和输出上限

多维检索模块新增模型适配器，不修改全局 Agent 客户端：

- SGLang/DashScope OpenAI 兼容请求传入 `chat_template_kwargs.enable_thinking=false`；
- Xinference 请求传入 `enable_thinking=false`；
- 测试桩和其他兼容客户端继续走原接口，但同样受两路信号量限制；
- 逐例输出上限由 2048 调整为 1536；
- 报告综合由 3072 调整为 2304；
- 整批图表启示由 768 调整为 640。

清理 `<think>` 仍保留为兼容保护，但不再把“生成后删除思考文字”当作关闭思考模式。

### 4. chunk 并发共享请求与图片延迟下载

`CompanyDocumentChunkStore` 使用有界线程池批量获取同一个例的 chunk，并通过 `inflight` Future 共享正在执行的相同 chunk 请求。返回结果始终恢复调用方传入的 chunk 顺序，缺失 chunk 继续跳过。

逐例分析前只读取候选图片的元数据、图注、页码和来源，不下载图片文件。模型返回图片引用后，先核对正文是否确实引用对应图号或图题，再只下载最终入选图片。图片下载失败的记录不会进入网页或 PDF。

### 5. 报告级并行与图表资产复用

所有逐例指标和分析完成后，规则聚合、强度汇总表和图表规格先在本地生成。报告综合调用与整批图表启示调用同时启动，二者只读取同一份规则统计事实，不相互依赖；完成后统一合并。

分析阶段生成的统计图路径随 `answer_id` 保存。导出 PDF 时按相同顺序复用这些 PNG，不再重新渲染；只有旧缓存缺少完整图表文件时才降级重绘。网页和 PDF 因而共享图表内容、顺序和启示文字。

响应审计新增：实际逐例 LLM 并发数、思考模式状态、每例模型调用次数、准备阶段累计耗时、逐例分析累计耗时、报告并行阶段耗时和总流水线墙钟耗时。

## 十一、2026-08-26 全量指标事实库与六 chunk 分批提取改造

### 1. 问题

原逐例模型调用同时生成强度指标、三段正文和图片引用。虽然提示词中附带了数字证据句，但模型输出指标仍会受到正文生成、图片引用、输出长度和来源文本校验的共同影响；当个例关联 chunk 超过六个时，正文精选片段也容易让人误以为未选中的 chunk 不会参与指标判断。重点个例强度汇总因而可能在原文存在数值时仍显示缺失。

### 2. 新的指标提取链路

本次将指标提取从逐例正文调用中完全拆出，新增 `CaseMetricPipeline`：

1. 按当前个例 `source_chunk_ids` 读取全部正式关联 chunk；
2. 保持原文顺序，每六个 chunk 划分为一个独立指标批次；
3. 每个批次先由规则扫描完整原文，保留全部带来源的指标候选；
4. 再由模型仅对本批数字证据句进行补充归类，模型不生成正文、不选图、不跨批次取极值；
5. 后端汇总全部批次候选，按指标、数值、单位、来源 chunk 和原文证据去重；
6. 为完整指标目录显式记录 `confirmed` 或 `not_present_after_all_chunks_scanned` 状态；
7. 逐例正文、统计图和重点个例强度汇总均只读取该事实库。

因此，六 chunk 是单次模型批处理边界，不再是一个例的指标扫描边界。一个有 22 个关联 chunk 的个例会依次完成 4 批扫描，并在全部批次完成后统一取业务极值。

### 3. 正文与指标解耦

逐例正文调用仍只接收最多六个 rerank 精选分析 chunk 和候选图片图注，但其协议已调整为只输出 `analysis` 与 `cited_image_ids`，不再返回 `metrics`。这避免“正文写作质量、图片引用和指标完整性”三个任务相互挤占输出空间，也避免全量数字证据误导正文的天气机制分析。

### 4. 缓存和审计

- 新增独立目录 `case_metric_fact_cache`，缓存版本为 `case-metric-facts-v1-batched-six-chunks`，不复用旧联合调用缓存；
- 正文缓存版本升级为 `case-analysis-v20-analysis-only`；
- 响应 `audit.metric_fact_audit_by_case` 记录每例批次数、规则候选数、模型补充数、确认指标数和每个标准指标状态；
- 响应审计新增指标批次总数、每例最多指标批次调用数和每批固定 six-chunk 边界；
- 后端日志新增 `[多维检索][指标事实库]`，逐批记录 chunk 编号、规则候选数、模型补充数，以及最终完整扫描状态。

### 5. 表格前提与边界

重点个例强度汇总的动态列只能在指标事实库完成后再选择。表格不再承担“发现指标”的职责，只从所有已确认指标中按覆盖个例数选择字段。若某个例在全部关联正文中确实没有某项实况，该单元格仍显示“—”，不会用推测值填充。

### 6. 验证

- 新增回归测试：7 个 chunk 的个例中，关键积雪深度和过程降水量仅位于第 7 个 chunk，仍被成功写入事实库；
- 断言该个例被拆为 2 个六 chunk 批次，两个指标均为 `confirmed`；
- Python 编译检查通过；
- 新增回归测试：指标补充模型的每次上下文只包含一个六 chunk 批次，不能混入第七个 chunk；
- 新增回归测试：`24小时累计降水量 0.1-26.6mm` 此类省略连接词的范围表达，能够提取过程最大降水量 26.6mm；
- 本地单元测试扩展到 52 项并全部通过。

## 2026-08-26 共享 chunk 个例边界切分

### 1. 问题

本地标准个例的 `source_chunk_ids` 存在共享首尾 chunk。例如一个 chunk 可以同时包含前一个个例的预警服务结尾，以及下一个个例的标题和实况开头。原流程按 ID 读取完整 chunk 后直接进行指标扫描，会使相邻个例的数值进入同一个例，造成多行重复出现不属于本例的指标。

### 2. 处理方式

在 `CaseChunkAnalyzer.load_case_chunks` 增加个例正文归属切分：

1. 仍只读取当前个例 `source_chunk_ids` 指定的正式候选范围；
2. 按 `chunk_no` 拼接候选正文，并记录每个 chunk 的字符区间；
3. 在候选正文中匹配当前个例标题，标题前的文字视为前一例残留并剔除；
4. 从当前标题之后查找同一 PDF 中最早出现的其他标准个例标题，标题及其后的文字视为下一例内容并剔除；
5. 将保留字符区间映射回原 chunk，保持原始 `chunk_id`、顺序和溯源能力；
6. 标题未定位或切片为空时记录后端告警并保留正式关联范围，避免误判导致当前个例正文整体丢失。

所有后续环节，包括全量强度事实库、数字证据、rerank 精选正文和报告证据，均复用这批已裁剪 chunk。因此每次模型调用仍严格不超过六个 chunk，但不会再扫描相邻个例的数值。

### 3. 缓存与验证

- 指标事实库缓存版本升级为 `case-metric-facts-v2-batched-six-chunks-boundary-sliced`，旧的共享 chunk 提取结果不会命中；
- 新增回归测试，模拟首 chunk 同时包含前例 `303mm` 和当前个例标题、尾 chunk 同时包含下一例标题和 `46.8℃`；
- 断言裁剪后仅保留当前 `101.6mm`、`38.7mm/h` 和服务复盘文字，前后个例指标均被排除。

## 2026-08-26 主导灾种独立强度汇总表

### 1. 问题

原分组将寒潮、雨雪、降雪、暴雪和低温归入同一张强度汇总表。不同类型过程的实况指标口径并不相同，导致过程降水量、最低气温和降温幅度被同时放入一组动态列，出现大量无业务意义的“—”。

### 2. 处理方式

强度汇总继续保留“个例、主导灾种、并发灾害”三列固定字段，但按唯一主导灾种拆分为独立子表：大风、强对流/雷暴/冰雹、暴雨、寒潮/低温、雨雪、降雪、暴雪、高温、沙尘、雾和霜冻。每张子表只在该组个例的真实指标中选择最多三列动态字段，并优先选择组内每一个个例都有值的字段；共同完整指标少于三项时宁可少展示列，也不添加会产生“—”的字段。复合过程只进入其主导灾种表，其他灾种保留在“并发灾害”列。

### 3. 验证

- 新增回归测试，覆盖寒潮、大风、雨雪、降雪、暴雪五类个例；
- 断言五类个例分别落入 `cold_wave`、`wind`、`rain_snow`、`snowfall`、`blizzard` 五张不同的强度汇总表。

## 2026-08-26 大风表六列与预警阈值隔离

### 1. 问题

大风类表曾把最低能见度作为第三个动态字段。能见度属于雾、沙尘等灾种指标，不能因为大风过程伴随沙尘就作为大风强度代表。同时，4月20-21日过程的预警文字“预计阵风可达11-13级”被误作实况，覆盖了原文明确记载的29.2m/s（11级）。

### 2. 处理方式

大风表固定为六列：个例、主导灾种、并发灾害、最大风速、阵风等级、8级以上大风范围。第三个动态字段从正式实况正文提取，兼容“影响全省98%”与“429站/390站出现8级以上大风”两种写法；它反映覆盖范围，不再使用最低能见度。

规则提取和模型返回校验同时拒绝包含“预警区域”“预计”“未来24小时”“阵风可达”等语义的风速、风级数值。过程实测与预警阈值不再混合；指标事实库缓存升级，保证旧的13级错误结果不会复用。

另修正了共享 chunk 的标题定位：月度概览中的“主要过程列表”会重复出现正式过程标题，旧规则可能从目录标题开始并在下一章节标题前截断，导致4月11-13日过程只保留标题而丢失39.7m/s实况。现在优先定位带“一、/二、”章节编号的正式标题，再执行个例正文切分。

### 3. 验证

- 新增回归测试，断言大风表固定选择最大风速、阵风等级、8级以上大风范围三列；
- 断言4月11日过程保留39.7m/s（13级），4月20日过程保留29.2m/s（11级），预警13级不参与取值。
- 新增目录标题回归测试，确认4月11-13日正式章节的后续实况不会被同名目录条目截断。
