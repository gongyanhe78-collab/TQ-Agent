# 2026-08-26 个例分析诊断式复盘优化

## 问题

原逐例分析虽然限制了最多六个精选 chunk，但仍要求模型直接生成三段完整正文。模型容易顺着片段顺序重复概括，或在没有环流、预报服务等材料时按常见业务模板补写机制、预警提前量和泛化建议；同时，已在全量关联 chunk 中核验的强度指标没有作为正文生成的受控事实输入，导致正文与强度汇总之间缺少稳定衔接。

## 本次处理

1. 保持强度事实库和正文分析解耦。
   - 全部关联 chunk 仍由 `CaseMetricPipeline` 按每批最多六个 chunk 扫描并核验指标。
   - 逐例正文仍只读取 rerank 后最多六个分析 chunk，不把全部原始正文重复传给正文模型。
2. 将已核验强度事实加入正文模型上下文。
   - 每个标准指标按业务极值保留数值、地点和原始来源句。
   - 正文模型只能引用这些事实，不能改写数值、补造地点或重新判定极值。
3. 将正文模型输出改为五个诊断槽位：过程画像、关键致灾链、复合风险、预报服务复盘、可迁移启示。
   - 关键致灾链只在原文存在环流、热力、地形、雷达或明确演变证据时输出。
   - 预报服务复盘只在原文存在预报、预警、服务、偏差或提前量记录时输出。
   - 可迁移启示必须由本例的落区、演变或服务证据推导，禁止输出“加强监测”等泛化口号。
4. 后端将五个槽位和已核验强度事实组合为固定三段逐例复盘。
   - 第一段：过程归属、重点区域、已核验强度和过程画像。
   - 第二段：关键致灾链与复合风险。
   - 第三段：预报服务复盘与可迁移启示。
   - 槽位材料为空时，明确说明本例不能作出该项判断，不虚构机制、提前量或业务建议。
   - 五个非空槽位合计控制在约 260 至 330 个汉字，后端组合后的三段正文仍按约 360 至 480 个汉字验收。
   - 合并正文不足最低篇幅时，只补充实况口径、诊断证据和服务评价边界，仍不补写原文没有的天气机制或业务动作。
5. 正文缓存版本升级为 `case-analysis-v21-diagnostic-slots`，缓存键额外包含已核验指标及来源句，旧的直接三段生成缓存不会继续命中。
6. 六片段选择增加过程概况、环流/影响系统、预报服务、影响风险四类角色覆盖；在上限内优先替换重复角色片段，避免六段材料都只是实况描述。

## 验证

- 新增回归测试，确认模型提示词使用五槽位协议，已核验指标与来源句进入正文上下文，并由后端写入第一段。
- 新增材料不足测试，确认正文显式保留机理和服务评价边界，不出现“加强监测”等泛化建议。
- 新增六片段角色覆盖测试，确认重复过程概况片段会被环流和预报服务片段替换。
- 运行 Python 编译、模块单元测试和 `git diff --check`，结果以本次执行日志为准。
