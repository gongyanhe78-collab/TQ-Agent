# Smart_Case_Match Bug 修复记录（2026-08-19）

## 1. 修改范围

- 代码修改范围仅限 `backend/app/services/agent/Smart_Case_Match`。
- 本次只修复已核实的灾种标题门禁误判，以及客户端 `progress_id` 导致的任务状态和审计文件覆盖风险。
- 不改变候选数量、向量召回、Rerank、LLM 逐例提炼、综合研判和模型重试流程。

## 2. 宽泛天气标题被灾种门禁错误降权

### 问题详情

`matching.py` 原先仅使用 `DISASTER_TERMS` 判断历史个例标题是否包含灾种。这个词表用于从用户输入抽取标准灾种，因此没有独立的“降水”。但灾种家族中，“降水”是暴雨和强降水的合法宽泛标题表达。

本地真实个例 `FST2025-6-std-case-001` 的标题为“6月13-14日大范围降水过程”，其标准灾种包含强对流、暴雨、强降水和短时强降水。暴雨查询对该个例的灾种、时间和落区匹配均较高，但旧门禁因标题没有命中 `DISASTER_TERMS` 而返回失败，随后把结构化分额外乘以 `0.35`。

### 导致的问题及风险

- 真实同家族个例会被当成标题灾种不匹配，排序被不合理压低。
- 当月份或落区不能提供高分时，相关个例可能跌破 `0.30` 质量门槛，无法进入后续十五个候选和 LLM 深入比较。
- 如果直接把“降水”加入用户灾种抽取词表，又会把宽泛天气现象错误变成一个不在标准枚举中的新灾种。

### 补救措施

1. 新增仅供历史标题判断使用的 `TITLE_DISASTER_TERMS`。
2. 该集合从标准灾种词和已有 `DISASTER_FAMILY` 自动推导，因此“降水”等家族宽泛词可以用于标题准入，但不会进入用户灾种抽取流程。
3. `_disaster_score()` 和 `_has_strong_disaster_match()` 统一使用标题识别集合，确保准入和标题冲突判断口径一致。
4. 保留标题冲突保护：例如暴雪查询面对只有“降水”标题的暖季个例时仍不能通过雨雪家族门禁，正文噪声标签也不能绕过限制。

### 验证结果

使用“暴雨、6月13-14日、全省”复核真实个例：

- 修复前：灾种门禁失败，结构化分 `0.3222`，候选排名第 5。
- 修复后：灾种门禁通过，结构化分 `0.9205`，候选排名第 3。
- 新增反向测试确认“暴雪查询 + 大范围降水标题”仍不能通过门禁。
- 原有“高温标题不能因正文暴雨标签得到高分”和“暖季降水不能冒充雨雪个例”测试继续通过。

## 3. 客户端进度号覆盖任务状态和审计文件

### 问题详情

`agent.py` 原先直接把请求中的 `progress_id` 当作 `run_id`。当调用方重复使用同一值时，后一次任务会覆盖进程内的前一次进度状态，审计日志也会写入同一个 `{run_id}.json`。

此外，`audit_log.py` 会把不适合文件名的字符替换为下划线，不同原始值可能得到同一个文件名，例如 `ab/c` 与 `ab_c`，后一次原子替换会覆盖前一个审计文件。

### 导致的问题及风险

- 两个并发或连续请求可能共享同一个任务主键，人工看到的进度不再对应唯一请求。
- 后写入的审计文件可能覆盖先前记录，导致十五个候选、最终选择和模型状态无法完整追溯。
- 单纯限制文件名字符只能避免路径穿越，不能保证清理映射是一一对应关系。

### 补救措施

1. 结构化入口和自然语言流式入口始终由服务端使用 UUID 生成唯一 `run_id`，客户端值不再作为任务主键。
2. 客户端 `progress_id` 改为进度查询别名。进度状态仍只按唯一 `run_id` 保存；旧页面继续使用原 `progress_id` 访问进度接口时，会解析到对应的服务端任务，不需要修改页面调用方式。
3. 同一客户端别名被重复使用时，只更新别名到最近任务的查询指向，两个服务端 `run_id` 对应的状态仍分别保留，可直接按各自 `run_id` 查询，不会互相覆盖。
4. 审计 JSON 新增 `client_progress_id` 字段，分别记录唯一运行号和客户端关联号，审计协议版本更新为 `1.1`。
5. 审计文件名清理发生字符替换时，追加原始值的 SHA-256 短摘要。`ab/c` 和 `ab_c` 因此生成不同文件名；路径字符仍不会进入实际文件名。

### 验证结果

- 新增测试确认同一个客户端别名对应的两个服务端任务状态同时存在，按各自 `run_id` 可独立查询。
- 新增 Agent 端到端断言，确认返回的 `run_id` 不等于客户端传入的 `progress_id`，且保持既有 `smart_case_` 前缀。
- 新增审计测试确认 `ab/c` 和 `ab_c` 生成两个不同且同时存在的 JSON 文件。
- 原有进度 TTL、路径穿越保护、审计原子写入和页面进度轮询测试继续通过。
