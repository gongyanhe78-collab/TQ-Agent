# Smart_Case_Match Bug 核实与修复记录（2026-08-18）

## 1. 检查范围与原则

- 检查范围仅限 `backend/app/services/agent/Smart_Case_Match`。
- 对外部检查报告列出的 18 项逐项核实，不把“潜在风险”直接当作已经发生的 Bug。
- 修复以保持现有候选检索、LLM 候选重排、逐例经验提炼和跨个例综合流程不变为前提。
- 不新增 LLM 调用时间限制，不改变逐例提炼的重试和降级策略，不修改模型提示词及最终个例数量。
- 新增代码注释均使用中文，说明边界处理或兼容原因。

## 2. 已确认并修复的问题

### 2.1 相对日期范围被截断

**问题详情**：`今天到后天`、`明天到后天` 会在命中第一个相对日期后立即返回，结束日期丢失。

**影响与风险**：查询过程被错误识别为单日，时间相似度、过程持续时间和候选排序可能失真；跨年时还可能生成错误年份。

**补救措施**：`natural_query.py` 先识别相对日期范围，再处理单个相对日期；范围两端均按服务当前日期换算，支持跨年。日期范围结束解析同时支持显式结束年份和跨年补年。

**验证**：新增 `今天到后天` 且当前日期为 12 月 31 日的回归用例，结果为当年 12 月 31 日至次年 1 月 2 日。

### 2.2 跨月、跨年图片日期误过滤

**问题详情**：历史个例为 `12月29日-1月3日` 时，旧逻辑只比较日号，无法表达跨月区间，可能把 1 月 1 日的相关图片过滤掉。

**影响与风险**：真正属于历史过程的形势图或实况图无法进入证据候选，降低可核验图片覆盖率，也可能触发证据不足。

**补救措施**：`nodes.py` 将个例范围和图注日期解析为完整月日，再按普通区间或跨年区间判断；仅在能够可靠解析时做日期拒绝，避免误删。

**验证**：`12月29日-1月3日` 保留 1 月 1 日图片，拒绝 2 月 1 日图片。

### 2.3 多样性选择恢复顺序依赖字典值相等

**问题详情**：`selected.sort(key=lambda item: ranked.index(item))` 依赖字典整体相等；中间节点一旦补充字段，恢复顺序会变得脆弱。

**影响与风险**：最终三个个例在字段增强后可能无法按原排序稳定恢复，甚至抛出 `ValueError`。

**补救措施**：`selection.py` 预先建立 `case_id -> 排名` 映射，最终只按稳定业务主键恢复原顺序。

### 2.4 SSE 心跳缺少当前进度

**问题详情**：长时间模型调用期间，心跳事件只有提示文字，没有 `percent` 和 `stage`。

**影响与风险**：前端在正常等待模型时无法维持当前进度显示，容易被误判为流程卡住。

**补救措施**：`agent.py` 的心跳读取最新进度状态，并携带当前 `percent` 和 `stage`；不改变后台节点执行顺序。

### 2.5 跨月、跨年持续时间被算成 1 天

**问题详情**：旧实现只用结束日减起始日，`7月31日-8月2日` 和 `12月29日-1月3日` 会得到负数并被压成 1 天。

**影响与风险**：持续时间维度明显失真，进而影响时间配置得分和最终排序。

**补救措施**：`matching.py` 解析起止年月日；缺省结束年份时根据月份回绕判断跨年，并使用日期差计算包含首尾的天数。

**验证**：7 月 31 日至 8 月 2 日为 3 天；12 月 29 日至次年 1 月 3 日为 6 天。

### 2.6 日期解析存在永远到不了的重复分支

**问题详情**：`_parse_calendar_date()` 的第三种格式已被第一种格式完全覆盖。

**影响与风险**：虽然不直接造成运行错误，但增加维护歧义，后续修改可能误以为两个分支行为不同。

**补救措施**：删除不可达的重复格式，保留原有可识别日期格式，业务行为不变。

### 2.7 本地 JSON 格式错误被静默伪装为空数据

**问题详情**：数据文件顶层不是数组、JSON 无法解析或数组成员不是对象时，旧实现直接返回空列表，健康检查无法区分“确实无数据”和“数据损坏”。

**影响与风险**：候选、文本块或图片元数据可能整体消失，但系统只表现为检索结果少，定位困难。

**补救措施**：`data_store.py` 仍采用空列表隔离坏文件，避免请求直接崩溃；同时记录明确的 `data_load_errors`，并把健康状态标记为 `degraded`。这是数据层故障可见性，不是 LLM 业务降级。

**验证**：构造对象顶层的 `standard_cases.json`，确认健康状态为 `degraded` 且包含具体错误。

### 2.8 审计明细同名字段互相覆盖

**问题详情**：各节点明细平铺到审计对象顶层，多个节点都写 `candidate_count` 等同名字段时，前面的值会被覆盖。

**影响与风险**：无法还原 15 个候选如何逐步变成最终 3 个个例，审计日志失去核验价值。

**补救措施**：`nodes.py` 新增 `audit.node_details[node]` 保存每个节点完整明细；同时继续保留旧的顶层字段，兼容已有页面和日志读取方。

**验证**：两个节点分别写入候选数 15 和 3，节点明细均可独立读取。

### 2.9 文本重叠采样策略不对称

**问题详情**：来源文本按 4 字步长采样，目标文本却逐字采样，重叠率计算两侧策略不一致。

**影响与风险**：证据文本去重和相似判断可能产生方向性偏差。

**补救措施**：`nodes.py` 两侧统一采用相同步长 4，保持原有性能约束并消除不对称。

### 2.10 个例开始日期可能误取“持续到 5 日”中的 5 日

**问题详情**：旧正则可能把只有结束含义的日号识别成过程开始日期。

**影响与风险**：证据窗口被错误后移，相关文本块或图片可能被排除。

**补救措施**：`enrichment.py` 只在存在明确“月份 + 起始日”或合法范围起点时返回开始日期；无法可靠判断时返回空值，让后续逻辑采用保守的不过滤行为。

**验证**：`3月持续到5日` 不再被识别为 3 月 5 日开始，`3月3-5日` 仍正确识别为 3 月 3 日。

### 2.11 进度状态长期累积

**问题详情**：全局进度字典没有清理机制，服务长时间运行会持续保留每次请求状态。

**影响与风险**：高请求量下内存缓慢增长；异常中断的运行中状态还会永久残留。

**补救措施**：`progress.py` 对完成/失败状态设置 2 小时 TTL，对异常遗留的运行中状态设置 24 小时保护 TTL；每次访问和写入时进行轻量清理。对外返回时移除内部时间字段，API 协议不变。

**验证**：过期的完成状态会删除，同一时刻仍在运行的状态继续保留。

### 2.12 综合研判来源过滤规则分散

**问题详情**：节点层只接受有效 LLM 来源，服务层仅排除 `rule_fallback`，两处规则表达不同，新增来源类型后可能出现审计数量和实际综合输入不一致。

**影响与风险**：规则降级摘要可能意外进入跨个例共识，或有效参考被某一层单独排除。

**补救措施**：`llm_schemas.py` 定义共享的 `VALID_REFERENCE_SOURCES`，节点和服务统一使用。对没有 `reference_source` 的旧直接调用保留兼容，只要调用方显式提供来源就严格按白名单过滤。

**验证**：现有综合研判、质量门和旧服务直接调用测试均通过，没有新增逐例提炼或综合研判降级。

### 2.13 相对日期规则遗漏“昨天到今天”

**问题详情**：上一版规则已处理“今天到后天”和“明天到后天”，但相对日期词表没有覆盖“昨天/昨日、前天/前日”。因此 `昨天到今天` 无法命中范围正则，随后单日兜底只命中“今天”，错误得到单日日期。

**影响与风险**：过去一天到当前日的过程会被压缩成当前单日；LLM 即使识别出正确范围，也可能被错误的规则结果覆盖，影响持续时间和时间相似度排序。

**补救措施**：补齐过去相对日期及所有合法范围组合；规则统一按 `Asia/Shanghai` 业务日期计算，逆序范围不伪造精确端点。LLM 改为只输出 `date_expression/date_evidence`，旧模型返回的精确日期仅用于冲突审计，不能进入排序。冲突明细写入自然语言请求的 `audit.date_resolution`。

**验证**：新增 `昨天到今天`、`前天到后天`、单独“昨日”和错误模型年份覆盖测试；页面同时展示日期范围两个端点。

### 2.14 综合研判暴露内部 ID，摘要在短语中间截断

**问题详情**：综合模型的结构化 `support_case_ids` 本来用于证据关联，但模型可能把 `FST...` 或 `chunk...` 直接写进自然语言正文；前端又直接显示这些字段。与此同时，`similarity_assessment` 和 `main_risk` 使用 55 字硬截断，可能把“系统移动”截成“系统移。”。

**影响与风险**：业务人员无法直接理解内部编号；摘要看起来像模型输出不完整，容易误判环流结论被截断或模型调用失败。

**补救措施**：

1. 综合提示词明确禁止在正文出现 `case_id/chunk_id/FST...` 等内部标识；后端对已知 case/chunk ID 做最后清理，case ID 替换为“年份 + 个例标题”，chunk ID 替换为“相关文字证据”。
2. 结构化 JSON 和审计日志继续保留原始 `support_case_ids/evidence_chunk_ids`，仅改变用户可见正文和页面元信息。
3. 页面根据已返回的匹配个例建立 `case_id -> 个例名称` 映射，摘要和提示中的“支持个例”显示业务名称；映射缺失时显示“相关历史个例”，不回退泄露内部 ID。提示证据只显示“可核验文字证据 N 条”，真实 chunk ID 继续保留在 JSON 和审计中。
4. 摘要提高合理长度上限，优先在完整句号、问号、分号等边界截取；没有完整边界时用省略号表示未完整展示，不再补造完整句号。

**验证**：新增测试确认正文不含 `FST...`、完整保留“系统移动”短语、结构化支持 ID 不变，页面元信息使用个例名称。

## 3. 核实后未按 Bug 修改的项目

### 3.1 小候选集的位置分差较大

报告所指 `total = max(1, len(normalized_hits) - 1)` 不会除零。两个结果得到 1.0 和 0.0 是当前仅在缺少供应商分数时使用的排名位置归一化，顺序正确。改变它属于评分策略调整，需要业务标注集评估，不能作为本次 Bug 修复直接修改。

### 3.2 重试 deadline 在休眠后未检查

经核实，`_call_with_retry()` 每轮循环开始都会重新计算剩余时间并在非正时退出；报告所称“重试后不再检查”不成立。当前正常链路也不设置总 deadline，因此未修改，避免重新引入用户已经取消的模型调用时间限制。

### 3.3 部分候选缺少 LLM 评估时的降权不对称

当前候选重排会用结构化维度补齐未被模型返回的候选；当整批模型评估不可用时，保留确定性的融合分排序是故障隔离策略，而不是对所有候选施加无证据惩罚。该项属于策略取舍，不能在没有离线排序标注集的情况下作为代码 Bug 修改。

### 3.4 线程池 `cancel_futures` 的 Python 3.8 兼容性

当前项目运行环境为 Python 3.10，代码中也已使用 Python 3.10 类型语法，因此 Python 3.8 不在当前兼容目标内。线程池和共享 HTTP 客户端的幂等关闭、关闭后禁止复用等生命周期保护已有专项测试，本次不做与业务缺陷无关的兼容改写。

### 3.5 `state.update(node_output)` 可能覆盖状态

逐节点核实后，节点返回值会先合并已有 `warnings` 和 `audit`，再交给状态更新，当前不存在已知丢失。为降低审计字段冲突风险，本次只增加了 `node_details`，没有改动图执行状态协议。

### 3.6 页面模板可能不存在

`chat_page.html` 和 `conversation_page.html` 均实际存在于当前目录，路由引用有效，因此报告中的前提不成立。

## 5. 业务流程影响说明

本次修改集中在日期边界、证据过滤、审计可观测性、进度生命周期和来源规则一致性，没有减少候选数量，没有跳过候选 LLM 重排，没有减少最终逐例 LLM 提炼次数，也没有用规则摘要替代有效 LLM 参考经验。外部模型服务自身的内容安全拦截、网络错误或持续返回不符合协议的结果仍属于不可由本地代码绝对消除的外部故障；现有重试、协议修复和明确降级机制保持不变，避免一次异常导致整个请求失败。

## 6. 本次追加优化：专业术语跨灾种迁移

**问题详情**：综合研判提示词原先存在跨场景复用专业词的风险。模型可能把某个雨雪个例中的“冷垫”等概念迁移到夏季暴雨、沙尘或其他灾种，生成语义上看似专业、但当前过程和支持证据均无法证明的提示。仅靠维护一份全局“禁用词”列表不可扩展：灾种、月份和业务指标会持续增加，同一个词在不同配置下也可能合法或不合法。

**影响与风险**：业务人员会把不适用的概念误认为当前过程的诊断依据，降低综合研判可信度；错误术语还可能把无关个例经验包装成跨个例共识，影响后续预报决策。

**补救措施**：

1. 从现有 `dimension_profiles.py` 的灾种配置动态构造术语上下文，区分通用词、当前灾种配置词和其他灾种专属词，并把当前月份、灾种和配置一起传给综合模型。多灾种输入合并全部已识别配置，不再由单一“主灾种”硬编码决定术语范围。
2. 综合提示词明确要求：专业术语必须符合当前月份和灾种配置，并能在当前过程原文或该提示声明的支持个例证据中追溯；没有证据时使用中性表述，不能从其他灾种模板迁移。模型仍负责理解和组织语言，后端规则负责最终边界校验。
3. 对模型输出中的配置术语逐字段检查。发现无证据术语或跨灾种术语时才调用一次定向 `cross_case_terminology_repair`，只允许改写术语，不得新增事实、个例或证据；修复后重新校验。正常输出不增加额外模型调用。
4. 若外部模型修复仍失败，后端只把违规词替换成“相关配置”等中性表述，保留原有结构、支持个例 ID 和证据 ID，避免错误专业概念直接展示，也不把该问题扩大为整条链路降级。

**验证**：新增暴雨场景回归测试，构造模型错误输出“冷垫”，确认第一次综合结果触发定向修复，第二次输出改用有证据的“水汽输送、低层急流、小时雨强”，最终正文不再包含“冷垫”；同时验证当前配置中的“降水演变”在没有当前过程或支持证据时会被识别为无依据术语。目录内完整测试共 84 项，全部通过（`OK`）。
